JointTrajectoryControllerによるアーム制御の基本

JTCの実装4ステップ

  1. 手先のwaypoints決定
  2. 逆運動学
  3. 軌道・軌跡生成
  4. 実行

step1:waypointsの計算

  • 位置とクオータニオンの7次元を並べてwaypointsを作成
  • クオータニオンのSlerpを活用すると動作が滑らかになる

手先姿勢の表現

位置(position)+向き(orientation)=姿勢(pose)

  • 位置：XYZで表す
  • 向き：オイラー角 or クオータニオン
  • ROSでは内部計算でクオータニオンを使う

実用上は最初と最後の姿勢をオイラー角で指定、クオータニオンに変換後に補完してROSに渡す

オイラー角による表現と課題

アプリ全画面

  • 利点
    • 直観的
    • 3つの角度（Roll, Pitch, Yaw）で表現
  • 課題
    • ジンバルロックを避ける必要
    • 軌道補間で不自然な動きになることがある

クォータニオンによる表現

アプリ全画面

  • 利点
    • ジンバルロックが発生しない
    • 回転軸と回転角で表現
    • 数値的に安定
  • 課題
    • 直観的理解が困難
    • 4つの要素（w, x, y, z）で表現
    • 正規化が必要

クォータニオン補間の利点

アプリ全画面

  • SLERP (Spherical Linear Interpolation)
    • 球面上の最短経路で補間
    • 角速度が一定
    • 滑らかな軌道生成
  • オイラー角補間との比較
    • より自然な回転軌道
    • ジンバルロック回避
    • 計算効率が良い

クォータニオンを扱う方法

  • TF
    • ROS標準
    • ROS専用の型を使えるのが便利
  • Scipy Rotation
    • ROS不要でクオータニオンの計算が可能
    • SLERPもあるので僕はよく使う

姿勢の表現 - オススメの実装

  • 最初と最後の姿勢は直観的にわかりやすいオイラー角で指定
  • 最初→最後の間のwaypointsの計算ではオイラー角→クォータニオンに変換してSlerpで補完
  • ROSはクオータニオンしか扱えない点に注意

step2:逆運動学(IK)

XYZでロボットの手先姿勢を指定したい
ただ、動かせるのはロボットの関節
そこで手先姿勢→ロボットの関節の計算をする(逆運動学,IK=InverseKinematics)

逆運動学の解き方(IKソルバー)

アプリ全画面

  • 解析解
    • 特定のロボット構造に基づいた数式
    • 関節角度を直接計算
  • 数値解
    • 最適化計算による近似解法
    • 左のアプリのように徐々に近づける

現在は汎用性が高く速度も精度も十分になったので数値解を使うことが多い

MoveItのIKソルバーの利用

MoveItのIKソルバーをROS Serviceを介して使うのが簡単

通信時間がかかるので大量のIKには使いにくい、数点のIKなら実用的

  • KDL - ニュートン法の数値解ソルバー, MoveItでデフォルト
  • TRACK-IK - 数値解ソルバーでニュートン法とSQP(逐次二次計画法)のハイブリッド, KDLより収束性が良い, Universal RobotのMoveItでデフォルト
  • IKFast - 解析解ソルバー, 計算は早いが解を安定して得にくい

Pythonで使えるIKソルバー

大量のIKを解く際は以下のようなIk用ライブラリを直接使うのが良い

  • TRACK-IK-PYTHON(オススメ) - MoveItでも使われている手法, 安定性と計算速度のバランスが良い
  • Pinocchio - 最先端の剛体アルゴリズムを実装したライブラリ, Franka Roboticsのライブラリでデフォルト

軌跡・軌道生成

  • 軌跡：逆運動学で得た解, 時間情報なし
  • 軌道：時間情報を加えたもの

    • ※軌跡と軌道の言葉の定義は書籍「実践 ロボット制御」での定義を使っています

  • JointTrajectoryControllerでは、少なくともPositionとTimeFromStartを渡すと軌道計算と実行が可能
  • 振動を抑える場合は厳密な速度, 加速度が必要だが、実用上はpositionだけでも問題ないことも多い

JointTrajectoryの送信方法

  • Topic(こっちは簡易的、もしくは連続でGoalを 送る場合)
    • /joint_trajectory_controller_name/commandに送信
    • 送ったら直ちに動作を実行、途中で止められない
  • Action(基本はこっちを使う)
    • /joint_trajectory_controller_name/FollowJointTrajectoryに送信
    • 目標到達までの状態確認や途中変更も可能

Actionで送った場合の利点

参考資料: joint_trajectory_controller.md

  • 途中でキャンセルしたり、軌道を変更して滑らかに繋ぐことができる
  • 即時に反映したいとき以外は基本的にActionを使うべき

JointTrajectoryControllerのテスト方法

  • rqt_joint_trajectory_controller_guiが便利
  • JointTrajectoryControllerが正常に動いているのかをテストするときなどに使える

JointTrajectoryControllerによるアームの速度・加速度制御

速度・加速度制御は必要か？

ここまで紹介した手法の課題

  • 急加速、急減速
  • 動作に振動が出やすい

軌道補間の方法

アプリ全画面

主な補間方法

  • 線形補間 - 最も単純
  • 3次スプライン - 滑らかな位置と速度
  • 5次スプライン - 滑らかな位置、速度、加速度
  • 台形 - 動作が速い

※教科書で出てくる時間多項式とスプラインは等価です
2点→時間多項式, 複数点→スプラインという違いです

補間方法の比較まとめ

補間方法 計算コスト 滑らかさ 連続性 適用場面
線形補間 低 低 C⁰ 高速動作・簡単制御
3次スプライン 中 中 C¹ 一般的なロボット制御
5次スプライン 高 高 C² 高精度作業・振動抑制
台形補間 低 中 C¹ 高速動作・効率重視

迷った場合は3次スプラインが無難

関節速度計算はなくても良い

waypointsが少ないと波打つ

waypointsを増やす滑らか

  • 2点であれば「速度 and/or 加速度を0」
  • 3点以上であっても十分細かいwaypointsをとれば「速度 and/or 加速度を0」でも割となめらか

※ ただし全点で速度0 ＝ 全点で一度止まる動き。詳しくは次章「軌道の滑らかさ」

それでも厳密な速度計算が必要という方は↓

速度・加速度つき JTC 実装

  • 5次多項式ベースで軌道点を細かく作り、各区間の始端と終端で速度・加速度を 0 にそろえます
  • ros_study/jtc_velocity_accel_demo.pyで保存

関節速度の計算方法

アプリ全画面

ヤコビアンとは

  • 関節速度 → 手先速度
  • 微分の連鎖律から導出
  • 関係式：v = J * q̇
  • v: 手先速度ベクトル（6次元）
  • J: ヤコビアン行列（6×n）
  • q̇: 関節角速度ベクトル（n次元）

逆ヤコビアンによる手先速度の計算

アプリ全画面

逆ヤコビアン

  • 手先速度 → 関節速度
  • 式：q̇ = J⁻¹ * v

Jが正方行列でない場合は？

  • 疑似逆行列：J⁺ = Jᵀ(JJᵀ)⁻¹
  • 特異点対策：Damped Least Squares
  • 冗長性解決：Null Space制御

復習：止まるか丸めるか

角（ρ = 0）は止まるしかない／丸めれば vmax = √(amax ρ) 　アプリ全画面

幾何の滑らかさ(G)と時間の滑らかさ(C)を分ける

G：幾何連続性

経路の形の滑らかさ

どんな速さでなぞっても変わらない

C：時間連続性

時間の関数 p(t) としての滑らかさ

モータが実際に受け取る量

速度 > 0 で通過するとき、Gk の経路からは Ck の軌道までしか作れない

連続性の階層

経路の幾何達成できる時間連続性不連続になる量物理的な意味
G⁰ のみ（接線が折れる）C⁰速度通過不可。止まるしかない
G¹（接線連続：円弧ブレンド）C¹加速度通れる。トルクが段差状に飛ぶ
G²（曲率連続：クロソイド等）C²ジャークトルクが連続。実用上の合格線
G³C³ジャークの微分高速・柔軟な機構で意味を持つ

C¹ は「止まらずに通れる」最低条件
「振動させない」条件は C²（＝ G²）

なぜ G¹ では C² にできないのか

  • 直線 → 円弧の境目で曲率 κ = 1/ρ が段差状に跳ぶ
  • an = v²κ を連続に保つには v² が逆向きに跳ぶ必要がある
  • 速度 v は連続なので不可能。例外は v = 0 のときだけ
  • → 曲率の不連続は加速度の段差を強制する

加速度 ＝ 時間則 ＋ 幾何

p″ = s″ t（時間則・接線方向）＋ (s′)² κ n（幾何・法線方向）

アプリ全画面 　経路が完璧な円弧でも、時間則が台形なら加速度は段差。逆も同じ

ROS の軌道生成は3段構造

① 幾何パス

出力：関節空間の密な点列
（時間情報なし）

✗ 角があれば残る（G⁰）

② 時間パラメータ化

✓ 速度・加速度の上限

✗ TOTG はジャーク無制限

→

③ 補間

joint_trajectory_controller

入力：JointTrajectory
点と点の間を多項式でつなぐ

✓ 5次なら節点で C²

✗ 点の情報が欠けると次数が落ちる

この流れ自体は標準的な正攻法。ただしチェックすべき点が5つある↓

チェック①：幾何精度は密度で解決できる

e ≈ Δ² / (8R)

  • 直交空間で密にサンプリング → IK → 関節空間でつなぐ
  • ずれは弦と弧の差で Δ² に比例して縮む
  • 例：Δ = 10 mm, R = 100 mm → e ≈ 0.13 mm
  • MoveIt の compute_cartesian_path（eef_step）がやっていること

チェック②：5次が本当に5次になっているか

JointTrajectoryPoint に入れた情報実際の補間連続性
positions のみ線形C⁰（速度が飛ぶ）
positions + velocities3次（Hermite）C¹（加速度が飛ぶ）
positions + velocities + accelerations5次C²
 

point = JointTrajectoryPoint()
point.positions = q
point.velocities = dq       # 空だと線形補間
point.accelerations = ddq   # 空だと静かに3次に落ちる
  • 5次の6係数 ＝ 両端の 位置・速度・加速度（3条件 × 2）→ C² でつなぐため
  • 点が密なほど、次数が落ちたときの段差が頻繁に出る

補間次数を比べる

アプリ全画面 　同じ waypoint でも、点に入れる情報で加速度の形がまったく変わる

※ 5次でも節点で連続なのは加速度まで。ジャークは節点で折れる（実用上は十分）

チェック③：時間パラメータ化はジャークを抑えているか

  • MoveIt 2 の既定 TOTG（Time-Optimal Trajectory Generation）は時間最適
  • 時間最適 ＝ 常にどこかの制約が飽和 ＝ 加速度は bang-bang
  • 5次で C² につないでも、入力の加速度が飽和値を行き来すれば急変する
  • ジャークを抑えたいなら Ruckig（MoveIt 2 の AddRuckigTrajectorySmoothing）

チェック④：密にしすぎても滑らかにはならない

  • 制御周期より短い区間は意味がない
    • UR：CB3 系 125 Hz（8 ms）、e-Series 500 Hz（2 ms）
  • 区間が極端に短いと5次多項式の係数が悪条件になり、わずかな不整合が高周波成分になる
  • 密にするほど、節点の不連続が高周波になるだけ
  • 滑らかさを決めるのは密度ではなく、節点での連続性の次数

※ 前章の「速度・加速度を 0」にする方法は、全点で止まる（全点が r = 0 の停止点）のと同じ。補間次数のアプリで確認できます

チェック⑤：角は密にしても消えない

  • 直交経路に鋭い角があると、密にサンプリングしても角は点と点の間に残る
  • 時間パラメータ化は加速度制約を守るので、角で自動的にほぼ停止まで減速
  • ＝ ブレンド半径を使わない代わりに、角で勝手に遅くなる
  • 速度を保ちたいなら、幾何の側で自前のブレンドやスプラインを入れる

「精度と速度の交換」はレイヤーを変えても消えない

おまけ：特異点

  • 直交空間で滑らか ≠ 関節空間で滑らか
  • 特異点の近くでは q′ = J⁻¹ v の関節速度が発散する
  • compute_cartesian_path に jump_threshold があるのはこのため
  • 密な IK サンプリング方式で一番危険なのはここ

ヤコビアンと特異点は「速度・加速度制御」の章のアプリで確認できます

実務上の判断

ジャークはまず問題にならない

  • 低速の動作
  • 軽いペイロード
  • 例：多くのラボオートメーション

ジャークが効いてくる

  • 高速の動作
  • 長い・柔らかいペイロード
  • 液体を持っている：液面のスロッシングが固有振動を持つ → こぼれ・液滴残り

まとめ：ペンダントのパラメータと ROS の実装は同じ話

レイヤーUR（ティーチングペンダント）ROS
経由点の扱い（幾何）ブレンド半径 r自前でブレンド・スプラインを入れる
（入れなければ角で減速）
時間則コントローラ内部で自動TOTG（必要なら Ruckig で平滑化）
補間コントローラ内部で自動JTC：点に入れた情報で次数が決まる
  • どれも an = v² / ρ から出てくる
  • C¹ は「止まらずに通れる」最低条件、振動させない条件は C²
  • C² には幾何と時間則の両方が滑らかである必要がある

サンプリングベースの手法(RRT)

MoveItのデフォルト

  • ランダムにパスを伸ばして障害物がなかったら採用、を繰り返す
  • 実際は後処理をかけてスムーズに
  • スタートとゴールから同時に伸ばし収束性を良くしたRRT Connectが使われる

最適化ベースの手法(CHOMP)

  • コスト：障害物の距離を遠く、軌道の距離を短く、など
  • 最適化：勾配降下法
  • コストの設計と初期軌道の引きの良さによって収束時間や得られた軌道の良しあしが決まる
  • 障害物が多い実用場面では正直使いにくい

最適化ベースの手法(STOMP)

  • コスト：障害物の距離を遠くなど
  • 最適化：確率的最適化
  • 軌道は最適化で決めるけど、最適化はサンプリングベースというハイブリッドっぽい
  • 滑らかさはCHOMPより劣るが解が収束しやすく実用上は使いやすい

MoveIt Planning Sceneによる障害物設置

MoveIt Planning Scene の設置方法

GUIで追加する場合

  • RViz の MoveIt 画面で Planning Scene を確認しながら障害物を追加・調整します
  • 形状や位置を見ながら試行錯誤できるので、寸法合わせや初期確認に向いています

スクリプトで追加する場合

  • /planning_scene に CollisionObject を publish して障害物を追加します
  • launch に組み込めるので、毎回同じ環境を再現できます
  • 実機運用では「テーブルや乳鉢を自動で読み込む」構成にしておくと扱いやすいです
  • この講義では、再利用しやすいように load_planning_scene ノードとして実装します

追加する CPP コード1: load_planning_scene.cpp

  • table と mortar を Planning Scene に追加する本体です
  • 起動時に既存オブジェクトを削除してから、テーブルと乳鉢を登録します
  • 今回は mesh の代わりに box で乳鉢の内側領域を近似しています

追加する CPP コード2: load_planning_scene_main.cpp

  • PlanningSceneLoader を standalone ノードとして起動するための main() です
  • launch から呼べる実行ファイルにするために追加します
  • パラメータ override を受け取れるように NodeOptions を設定しています

追加する HPP コード: load_planning_scene.hpp

  • PlanningSceneLoader クラスの宣言です
  • publisher, timer, 障害物追加用メソッドをまとめています
  • C++ の実装を .cpp と分離して見通しを良くします

設定ファイル: planning_scene_config.yaml

  • テーブル位置や乳鉢位置など、planning scene の寸法と配置を YAML で管理します
  • config/planning_scene_config.yaml で保存

Launchファイル

  • load_planning_scene.launch.pyで保存
  • planning_scene_config.yaml をパラメータとしてノードに渡します
  • planning scene の読み込みを単体で実行できる構成にしています
