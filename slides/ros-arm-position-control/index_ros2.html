位置制御とは

手先を目標の位置・姿勢へ動かす制御。動かし方は大きく3種類

基本の動作指令（付属コントローラでもできる）
① PTP ゴールに着けばOK
② CP 途中の経路も指定
ROS・研究用途で多い
③ パスプランニング 障害物回避の経路を計算

①②は振り返り、③がROSで加わる部分↓

PTP（Point To Point）

制御の種類（ざっくり）

考え方得意・不得意ロボットでの例
古典制御伝達関数（周波数）で 1入力1出力を設計簡単・調整しやすい／多入力は苦手関節ごとの PID
現代制御状態方程式（時間）で多入力多出力を設計全体をまとめて最適化／モデルが必要LQR、カルマンフィルタ
MPCモデルで少し先を予測し、毎周期最適な入力を解く関節限界などの制約を直接扱える／計算が重い歩行ロボット、自動運転
強化学習試行錯誤と報酬で動かし方（方策）を学ぶモデル化が難しい動きに強い／大量の試行と Sim-to-real が課題四足歩行、把持

参考：こんとろラボ「制御の種類・分類」

PID 制御

  • P：誤差に比例した指令で目標へ近づける（基本）
  • I：誤差を積算し、残り続けるずれ（重力・摩擦などの偏り）を消す
  • D：誤差の変化の速さを見て、行き過ぎ・振動を抑える
  • UR などはロボット内部で回っている（JTC の gains は速度/トルク指令時）

位置制御は PD、力制御は PI

位置制御力制御
基本PD（ずれが残るなら PID）PI（目標力のフィードフォワード＋PI）
D収束を速め、振動を抑える急変・ノイズを増幅 → 制御の遅れで発散しやすい
IP だけでも動くことが多い。重力・摩擦の偏りが残るときに足す摩擦などの偏りを消すのに必要

JointTrajectoryControllerによるアーム制御の基本

JTCとは

JointTrajectoryController

  • 「関節の目標値＋到着時刻」の点を並べて送る
  • コントローラが時刻どおりに点から点へ動かす
  • 点の間はコントローラが補間する

JTCの実装4ステップ
（JTC = JointTrajectoryController）

  1. 手先のwaypoints決定
  2. 逆運動学
  3. 軌道・軌跡生成

step1:waypointsの計算

  • 目標の姿勢をたくさん並べてwaypointsを作成
  • 例：円やらせんの上に点を並べる

手先姿勢の表現

位置(position)+向き(orientation)=姿勢(pose)

  • 位置：XYZの3つで表す
  • 向き：手先座標系の傾き
  • 向きの表し方は複数ある（オイラー角・クォータニオン…）
  • ROSではクォータニオンをよく使う

オイラー角による表現と課題

アプリ全画面

  • 利点
    • 直観的
    • 3つの角度（Roll, Pitch, Yaw）で表現
  • 課題
    • ジンバルロックを避ける必要
    • 軌道補間で不自然な動きになることがある

クォータニオンによる表現

アプリ全画面

  • 利点
    • ジンバルロックが発生しない
    • 回転軸と回転角で表現
    • 数値的に安定
  • 課題
    • 直観的理解が困難
    • 4つの要素（w, x, y, z）で表現
    • 正規化が必要

クォータニオンってなに？

  • どんな向きも1本の軸まわりの1回の回転で表せる
  • その軸と角度を4つの数に詰めたもの

w = cos(θ/2)
(x, y, z) = n·sin(θ/2)

例：z軸まわりに90° → (w, x, y, z) = (0.707, 0, 0, 0.707)

ジンバルロックしない理由

オイラー角：3つの軸で順番に回す
クォータニオン：1軸で1回だけ回す
  • ジンバルロックは「軸を順番に回す」表し方の副作用
  • クォータニオンは向きを丸ごと1つの回転として持つので、特別な角度がない

なぜ正規化が必要？

  • qで回すとベクトルの長さは|q|²倍
  • |q| ≠ 1 だと回転に伸び縮みが混ざる
  • 実装（回転行列に変換）では姿勢もずれる（60°→69°）
  • 計算を重ねると誤差が積み重なって|q|が1からずれる
  • → q / |q| で長さ1に戻す

クォータニオン補間の利点

アプリ全画面

  • SLERP (Spherical Linear Interpolation)
    • 球面上の最短経路で補間
    • 角速度が一定
    • 滑らかな軌道生成
  • オイラー角の線形補間との比較
    • より自然な回転軌道
    • ジンバルロック回避
    • 計算効率が良い

なぜ球面線形補間（SLERP）？

  • クォータニオンは球面の上の点
  • 線形補間は球の内側を通る → 回る速さにムラ
  • 位置は綺麗でも向きの変化が不均一 → 手首が一部で急に速く回る
  • SLERPなら一定の角速度で回る

クォータニオンを扱う方法

  • TF
    • ROS標準
    • ROS専用の型を使えるのが便利
  • Scipy Rotation
    • ROS不要でクオータニオンの計算が可能
    • SLERPもあるので僕はよく使う

姿勢の表現 - 使い分け

最初と最後だけ指定（PTP的） → 人が読み書きしやすいオイラー角でOK
途中の姿勢も全部並べる（CP的） → クォータニオン＋SLERPで補間

おすすめ：両端はオイラー角で書く → クォータニオンに変換 → SLERP → ROSへ

ROSのメッセージ（geometry_msgs/Pose）はクォータニオンしか受け付けない点に注意

step2:逆運動学(IK)

XYZでロボットの手先姿勢を指定したい
ただ、動かせるのはロボットの関節
そこで手先姿勢→ロボットの関節の計算をする(逆運動学,IK=InverseKinematics)

IKの解き方は2種類

  • 解析解：ロボットの形から式を作り、代入して一発で解く
    • 速い・解が全部出る／ロボットごとに式が要る
  • 数値解：今の姿勢から少しずつ近づける（反復計算）
    • どのロボットでも使える／初期値しだいで失敗も

今は汎用性が高く、速度・精度も十分な数値解が主流

アプリ全画面

数値解のカギ：ヤコビアン

  • ヤコビアン J：関節を少し動かすと手先がどれだけ動くかの表
    • Δx ≈ J Δq（関節の微小変化 → 手先の微小変化）
  • 逆向きに使うと Δq ≈ J⁻¹ Δx（正方でなければ疑似逆行列 J⁺）
  • 目標との誤差を Δx として少しずつ詰める → 繰り返すと解に収束

IKの式を解かなくても、J さえ計算できれば数値的に解ける

J の詳細は「速度・加速度制御」の章で

補足：2種類のヤコビ行列

ヤコビ行列基礎ヤコビ行列
作り方手先姿勢（位置＋オイラー角）の式を q で偏微分根元のリンクから手先へ漸化的に外積で計算
計算量自由度が増えると微分が大量で重い外積だけなので軽い
得られるものJ(q) が q の式（解析解）で得られる今の姿勢での数値だけ
特異姿勢式から事前に求められる事前には求めにくい

今は計算が速いので、数値解をたくさん求めれば十分実用的
→ 基礎ヤコビ行列を使うことが多い

補足：基礎ヤコビ行列の作り方

  • 根元のリンクから順に、各関節の軸 zᵢ と位置 pᵢ を求める（順運動学のついで）
  • 手先速度ベクトル V = (v, ω)（並進速度＋角速度）を定義し
    基礎ヤコビ行列 JB：V = JB q′ を使う
  • 関節 i の列 = [ zᵢ × (p − pᵢ) ; zᵢ ] → 外積だけで計算できる

姿勢誤差は回転ベクトルで表して JB に掛ける（KDL などもこの方式）

特異姿勢（特異点）とは

  • J のランクが落ち、手先をある方向へ動かせない姿勢
  • 手先速度 v を指令すると q′ = J⁻¹ v が発散 → 関節が急回転
  • 一番困るのは速度の計算（直線動作・サーボ制御）
  • IK でも数値解が不安定に／解（肘上・肘下）がここで合流

対策：特異点を避けた経路・PTP（関節補間）で通過・DLS

特異姿勢は3種類

  • 肩：手首中心が J1 軸の真上 → J1 が急回転
  • 肘：腕が伸びきる（J3 = 0）→ 外へ動けない
  • 手首：J5 = 0 で J4 と J6 が一直線 → J4・J6 が逆向きに急回転

どれも手先は一定速度なのに、近くを通るだけで関節速度が上限を超える

KDL と TRAC-IK の違い

  • KDL：ニュートン法そのもの
    • 関節制限にぶつかると行き詰まることがある
  • TRAC-IK：KDL＋SQP を同時に走らせ、行き詰まったら別の初期値からやり直す
    • 成功率が高い → UR の MoveIt でもデフォルト
  • IKFast：解析解を自動生成（「IKの解き方は2種類」のアプリ）

アプリ全画面

MoveItのIKソルバーの利用

MoveItのIKソルバーをROS Serviceを介して使うのが簡単

通信時間がかかるので大量のIKには使いにくい、数点のIKなら実用的

  • KDL - ニュートン法の数値解ソルバー, MoveItでデフォルト
  • TRAC-IK - 数値解ソルバーでニュートン法とSQP(逐次二次計画法)のハイブリッド, KDLより収束性が良い, Universal RobotのMoveItでデフォルト
  • IKFast - 解析解ソルバー, 計算は早いが解を安定して得にくい

Pythonで使えるIKソルバー

大量のIKを解く際は以下のようなIk用ライブラリを直接使うのが良い

  • TRAC-IK-PYTHON(オススメ) - MoveItでも使われている手法, 安定性と計算速度のバランスが良い
  • Pinocchio - 最先端の剛体アルゴリズムを実装したライブラリ, Franka Roboticsのライブラリでデフォルト

JointTrajectoryControllerによるアームの速度・加速度制御

速度・加速度制御は必要か？

ここまで紹介した手法の課題

  • 急加速、急減速
  • 動作に振動が出やすい

軌道補間の方法

同じ経由点でも、点の間のつなぎ方（補間）で動きと揺れが変わる （アプリ全画面）

※教科書の時間多項式とスプラインは等価（2点→時間多項式、複数点→スプライン）

補間方法の比較まとめ

補間方法 計算コスト 滑らかさ 連続性 適用場面
線形補間 低 低 C⁰（速度が飛ぶ） 高速動作・簡単制御
3次スプライン 中 中 C¹（加速度が飛ぶ） 一般的なロボット制御
5次スプライン 高 高 C²（ジャークが飛ぶ） 高精度作業・振動抑制
台形補間 低 中 C¹（加速度が飛ぶ） 高速動作・効率重視

迷った場合は3次スプラインが無難

関節速度計算はなくても良い

waypointsが少ないと波打つ

waypointsを増やす滑らか

  • 2点であれば「速度 and/or 加速度を0」
  • 3点以上であっても十分細かいwaypointsをとれば「速度 and/or 加速度を0」でも割となめらか

※ ただし全点で速度0 ＝ 全点で一度止まる動き。詳しくは次章のコラム「軌道計画か、制御か」

JTCの補間次数の決まり方

JointTrajectoryPoint に入れた情報実際の補間連続性
positions のみ線形C⁰（速度が飛ぶ）
positions + velocities3次（Hermite）C¹（加速度が飛ぶ）
positions + velocities + accelerations5次C²
  • 5次の6係数 ＝ 両端の 位置・速度・加速度（3条件 × 2）→ C² でつなぐため
  • positions だけ送るとJTCは線形補間 → 経由点で速度が飛ぶ

補間次数を比べる

アプリ全画面 　同じ waypoint でも、点に入れる情報で加速度の形がまったく変わる

※ 5次でも節点で連続なのは加速度まで。ジャークは節点で折れる（実用上は十分）

速度・加速度つき JTC 実装

  • 5次多項式ベースで軌道点を細かく作り、各区間の始端と終端で速度・加速度を 0 にそろえます
  • ros_study/jtc_velocity_accel_demo.pyで保存

コラムMoveItの経路計画は実用的？

MoveIt 標準の RRT 系（OMPL）は障害物を避けられるが、現場では困ることも

🎲 結果が乱数しだい
同じ条件でも毎回違う経路になる
♾ 解けないことがある
「必ず解ける」は計算時間とメモリが無限のときの話。枝が壁の内側で増え続けて止まらない（デッドロック）
🧹 机の上をなぎ払う
関節空間では最短でも、作業空間では大回り → シミュレータに入れていない物にぶつかる
↪ 手先の向きが変わる
途中で手先が横を向く → 物を持ったピック＆プレースでは困る

参考: ロボットアームの動作計画（モーションプランニング）(Qiita) / 元論文（日本ロボット学会誌 40巻2号）

コラム現場の答え：トレース動作

始点と終点のロボット自身の体を、手先がなぞるように動く

  • ロボットの体があった場所には障害物がないことが確定している
  • アームは直鎖状なので、始点と終点の形をつなげば必ず1本の道ができる
  • IK を数回解いてつなぐだけ → 計算が軽い
  • 乱数に依存しない・原理が単純
  • 途中の手先の向きを指定できる
  • 小さな穴の通り抜けも解ける
  • 認識していない障害物にも当たりにくい

証明や最適化より、まず現実的に意味のある解を出せることが大事

参考: ロボットアームの動作計画（モーションプランニング）(Qiita) / 元論文（日本ロボット学会誌 40巻2号）

TFについて

  • TF = Transformの略
  • ROS標準搭載のシステムで、座標変換と座標の時間管理の2つの機能がある
  • 実装においてTFというと、実際は改良版のTF2のことを指す

機能1：座標変換

baseから見た乳棒手先
baseから見たヘラの手先
  • ここではTCPの座標変換を示したが、TFで管理された座標系であれば任意の座標変換が可能

座標変換の仕組み

  • TFはツリー構造になっている
  • 同姿変換行列で順々にツリーを辿って座標変換を計算

機能2：座標の時間管理

  • 関節角（/joint_states）から作った座標を時刻つきで保存している
  • 「いつの座標か」を指定して引ける
  • センサの値が遅れて届いても測った時刻の姿勢で変換できる
  • 古いデータはバッファから消える
