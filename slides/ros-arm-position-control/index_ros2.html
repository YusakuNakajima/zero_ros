位置制御とは

手先を目標の位置・姿勢へ動かす制御。動かし方は大きく3種類

基本の動作指令（付属コントローラでもできる）

② CP 途中の経路も指定
ROS・研究用途で多い

①②は振り返り、③がROSで加わる部分↓

振り返り：PTPとCP

PTP（Point To Point）
経路を規定しない・関節空間で補間
→ UR: movej()
CP（Continuous Path）
TCPの経路形状を規定・直交空間で補間
LIN 直線
→ movel()
CIRC 円弧
→ movec()
自由曲線

JointTrajectoryControllerによるアーム制御の基本

JTCとは

JointTrajectoryController

  • 「関節の目標値＋到着時刻」の点を並べて送る
  • コントローラが時刻どおりに点から点へ動かす
  • 点の間はコントローラが補間する

アプリ全画面

JTCの実装4ステップ
（JTC = JointTrajectoryController）

  1. 手先のwaypoints決定
  2. 逆運動学
  3. 軌道・軌跡生成
  4. 実行

step1:waypointsの計算

  • 目標の姿勢をたくさん並べてwaypointsを作成
  • 例：円やらせんの上に点を並べる

手先姿勢の表現

位置(position)+向き(orientation)=姿勢(pose)

  • 位置：XYZの3つで表す
  • 向き：手先座標系の傾き
  • 向きの表し方は複数ある（オイラー角・クォータニオン…）
  • ROSではクォータニオンをよく使う

オイラー角による表現と課題

アプリ全画面

  • 利点
    • 直観的
    • 3つの角度（Roll, Pitch, Yaw）で表現
  • 課題
    • ジンバルロックを避ける必要
    • 軌道補間で不自然な動きになることがある

クォータニオンによる表現

アプリ全画面

  • 利点
    • ジンバルロックが発生しない
    • 回転軸と回転角で表現
    • 数値的に安定
  • 課題
    • 直観的理解が困難
    • 4つの要素（w, x, y, z）で表現
    • 正規化が必要

クォータニオンってなに？

  • どんな向きも1本の軸まわりの1回の回転で表せる
  • その軸と角度を4つの数に詰めたもの

w = cos(θ/2)
(x, y, z) = n·sin(θ/2)

例：z軸まわりに90° → (w, x, y, z) = (0.707, 0, 0, 0.707)

ジンバルロックしない理由

オイラー角：3つの軸で順番に回す
クォータニオン：1軸で1回だけ回す
  • ジンバルロックは「軸を順番に回す」表し方の副作用
  • クォータニオンは向きを丸ごと1つの回転として持つので、特別な角度がない

なぜ正規化が必要？

  • qで回すとベクトルの長さは|q|²倍
  • |q| ≠ 1 だと回転に伸び縮みが混ざる
  • 計算を重ねると誤差が積み重なって|q|が1からずれる
  • → q / |q| で長さ1に戻す

クォータニオン補間の利点

アプリ全画面

  • SLERP (Spherical Linear Interpolation)
    • 球面上の最短経路で補間
    • 角速度が一定
    • 滑らかな軌道生成
  • オイラー角の線形補間との比較
    • より自然な回転軌道
    • ジンバルロック回避
    • 計算効率が良い

なぜ球面線形補間（SLERP）？

  • クォータニオンは球面の上の点
  • 線形補間は球の内側を通る → 回る速さにムラ
  • 位置は綺麗でも向きの変化が不均一 → 手首が一部で急に速く回る
  • SLERPなら一定の角速度で回る

クォータニオンを扱う方法

  • TF
    • ROS標準
    • ROS専用の型を使えるのが便利
  • Scipy Rotation
    • ROS不要でクオータニオンの計算が可能
    • SLERPもあるので僕はよく使う

姿勢の表現 - 使い分け

最初と最後だけ指定（PTP的） → 人が読み書きしやすいオイラー角でOK
途中の姿勢も全部並べる（CP的） → クォータニオン＋SLERPで補間

おすすめ：両端はオイラー角で書く → クォータニオンに変換 → SLERP → ROSへ

ROSのメッセージ（geometry_msgs/Pose）はクォータニオンしか受け付けない点に注意

step2:逆運動学(IK)

XYZでロボットの手先姿勢を指定したい
ただ、動かせるのはロボットの関節
そこで手先姿勢→ロボットの関節の計算をする(逆運動学,IK=InverseKinematics)

IKの解き方は2種類

  • 解析解：ロボットの形から式を作り、代入して一発で解く
    • 速い・解が全部出る／ロボットごとに式が要る
  • 数値解：今の姿勢から少しずつ近づける（反復計算）
    • どのロボットでも使える／初期値しだいで失敗も

今は汎用性が高く、速度・精度も十分な数値解が主流

アプリ全画面

数値解のカギ：ヤコビアン

  • ヤコビアン J：関節を少し動かすと手先がどれだけ動くかの表
    • Δx ≈ J Δq（関節の微小変化 → 手先の微小変化）
  • 逆向きに使うと Δq ≈ J⁻¹ Δx（正方でなければ疑似逆行列 J⁺）
  • 目標との誤差を Δx として少しずつ詰める → 繰り返すと解に収束

IKの式を解かなくても、J さえ計算できれば数値的に解ける

J の詳細は「速度・加速度制御」の章で

補足：2種類のヤコビ行列

ヤコビ行列基礎ヤコビ行列
作り方手先姿勢（位置＋オイラー角）の式を q で偏微分根元のリンクから手先へ漸化的に外積で計算
計算量自由度が増えると微分が大量で重い外積だけなので軽い
得られるものJ(q) が q の式（解析解）で得られる今の姿勢での数値だけ
特異姿勢式から事前に求められる事前には求めにくい

今は計算が速いので、数値解をたくさん求めれば十分実用的
→ 基礎ヤコビ行列を使うことが多い

補足：基礎ヤコビ行列の作り方

  • 根元のリンクから順に、各関節の軸 zᵢ と位置 pᵢ を求める（順運動学のついで）
  • 手先速度ベクトル V = (v, ω)（並進速度＋角速度）を定義し
    基礎ヤコビ行列 JB：V = JB q′ を使う
  • 関節 i の列 = [ zᵢ × (p − pᵢ) ; zᵢ ] → 外積だけで計算できる

姿勢誤差は回転ベクトルで表して JB に掛ける（KDL などもこの方式）

特異姿勢（特異点）とは

  • J のランクが落ち、手先をある方向へ動かせない姿勢
  • 手先速度 v を指令すると q′ = J⁻¹ v が発散 → 関節が急回転
  • 一番困るのは速度の計算（直線動作・サーボ制御）
  • IK でも数値解が不安定に／解（肘上・肘下）がここで合流

対策：特異点を避けた経路・PTP（関節補間）で通過・DLS

特異姿勢は3種類

  • 肩：手首中心が J1 軸の真上 → J1 が急回転
  • 肘：腕が伸びきる（J3 = 0）→ 外へ動けない
  • 手首：J5 = 0 で J4 と J6 が一直線 → J4・J6 が逆向きに急回転

どれも手先は一定速度なのに、近くを通るだけで関節速度が上限を超える

アプリ全画面

数値解のしくみ：ニュートン法

  • f(x) = 0 の x を、接線をたどって探す方法
  • 数ステップで答えにぐっと近づく
  • IKでは
    • x → 関節角 q
    • f → 目標と手先の誤差 e
    • 傾き → ヤコビアン J

タブ③で実際のアームに当てはめた様子が見られる

アプリ全画面

KDL と TRAC-IK の違い

  • KDL：ニュートン法そのもの
    • 関節制限にぶつかると行き詰まることがある
  • TRAC-IK：KDL＋SQP を同時に走らせ、行き詰まったら別の初期値からやり直す
    • 成功率が高い → UR の MoveIt でもデフォルト
  • IKFast：解析解を自動生成（タブ②）

アプリ全画面

MoveItのIKソルバーの利用

MoveItのIKソルバーをROS Serviceを介して使うのが簡単

通信時間がかかるので大量のIKには使いにくい、数点のIKなら実用的

  • KDL - ニュートン法の数値解ソルバー, MoveItでデフォルト
  • TRAC-IK - 数値解ソルバーでニュートン法とSQP(逐次二次計画法)のハイブリッド, KDLより収束性が良い, Universal RobotのMoveItでデフォルト

実行の中身：PID 制御

  • P：誤差に比例した指令で目標へ近づける（基本）
  • I：誤差を積算し、残り続けるずれ（重力・摩擦などの偏り）を消す
  • D：誤差の変化の速さを見て、行き過ぎ・振動を抑える
  • UR などはロボット内部で回っている（JTC の gains は速度/トルク指令時）

位置制御は PD、力制御は PI

位置制御力制御
基本PD（ずれが残るなら PID）PI（目標力のフィードフォワード＋PI）
D収束を速め、振動を抑える急変・ノイズを増幅 → 制御の遅れで発散しやすい
IP だけでも動くことが多い。重力・摩擦の偏りが残るときに足す摩擦などの偏りを消すのに必要

JointTrajectoryControllerによるアームの速度・加速度制御

速度・加速度制御は必要か？

ここまで紹介した手法の課題

  • 急加速、急減速
  • 動作に振動が出やすい

軌道補間の方法

同じ経由点でも、点の間のつなぎ方（補間）で動きと揺れが変わる （アプリ全画面）

※教科書の時間多項式とスプラインは等価（2点→時間多項式、複数点→スプライン）

補間方法の比較まとめ

補間方法 計算コスト 滑らかさ 連続性 適用場面
線形補間 低 低 C⁰（速度が飛ぶ） 高速動作・簡単制御
3次スプライン 中 中 C¹（加速度が飛ぶ） 一般的なロボット制御
5次スプライン 高 高 C²（ジャークが飛ぶ） 高精度作業・振動抑制
台形補間 低 中 C¹（加速度が飛ぶ） 高速動作・効率重視

迷った場合は3次スプラインが無難

関節速度計算はなくても良い

waypointsが少ないと波打つ

waypointsを増やす滑らか

  • 2点であれば「速度 and/or 加速度を0」
  • 3点以上であっても十分細かいwaypointsをとれば「速度 and/or 加速度を0」でも割となめらか

※ ただし全点で速度0 ＝ 全点で一度止まる動き。詳しくは次章「軌道の滑らかさ」

それでも厳密な速度計算が必要という方は↓

JTCの補間次数の決まり方

JointTrajectoryPoint に入れた情報実際の補間連続性
positions のみ線形C⁰（速度が飛ぶ）
positions + velocities3次（Hermite）C¹（加速度が飛ぶ）
positions + velocities + accelerations5次C²
  • 5次の6係数 ＝ 両端の 位置・速度・加速度（3条件 × 2）→ C² でつなぐため
  • positions だけ送るとJTCは線形補間 → 経由点で速度が飛ぶ

幾何の滑らかさ(G)と時間の滑らかさ(C)を分ける

G：幾何連続性

経路の形の滑らかさ

どんな速さでなぞっても変わらない

C：時間連続性

時間の関数 p(t) としての滑らかさ

モータが実際に受け取る量

速度 > 0 で通過するとき、Gk の経路からは Ck の軌道までしか作れない

G と C の対応

経路の形（G）止まらずに通ると実際どうなる
G⁰：角があるC⁰ まで通過不可。止まるしかない
G¹：円弧ブレンドC¹ まで通れる。トルクが段差状に飛ぶ
G²：曲率連続（クロソイド等）C² までトルクが連続。実用上の合格線

形が Gk なら、どんな時間則でも Ck が上限
「振動させない」には形から G² にする

C⁰/C¹/C² で何が飛ぶかは「速度・加速度制御」の章を参照

なぜ G¹ では C² にできないのか

  • 直線 → 円弧の境目で曲率 κ = 1/ρ が段差状に跳ぶ
  • an = v²κ を連続に保つには v² が逆向きに跳ぶ必要がある
  • 速度 v は連続なので不可能。例外は v = 0 のときだけ
  • → 曲率の不連続は加速度の段差を強制する

加速度 ＝ 時間則 ＋ 幾何

p″ = s″ t（時間則・接線方向）＋ (s′)² κ n（幾何・法線方向）

アプリ全画面 　経路が完璧な円弧でも、時間則が台形なら加速度は段差。逆も同じ

ROS の軌道生成は3段構造

① 幾何パス

OMPL / compute_cartesian_path

出力：関節空間の密な点列
（時間情報なし）

✓ 衝突回避・経路の形

✗ 角があれば残る（G⁰）

→

② 時間パラメータ化

TOTG（＋ Ruckig で平滑化）

出力：各点に時刻・速度・加速度

✓ 速度・加速度の上限

✗ TOTG はジャーク無制限

→

③ 補間

joint_trajectory_controller

入力：JointTrajectory
点と点の間を多項式でつなぐ

✓ 5次なら節点で C²

✗ 点の情報が欠けると次数が落ちる

この流れ自体は標準的な正攻法。ただしチェックすべき点が5つある↓

チェック①：幾何精度は密度で解決できる

e ≈ Δ² / (8R)

  • 直交空間で密にサンプリング → IK → 関節空間でつなぐ
  • ずれは弦と弧の差で Δ² に比例して縮む
  • 例：Δ = 10 mm, R = 100 mm → e ≈ 0.13 mm
  • MoveIt の compute_cartesian_path（eef_step）がやっていること

チェック②：5次が本当に5次になっているか


point = JointTrajectoryPoint()
point.positions = q
point.velocities = dq       # 空だと線形補間
point.accelerations = ddq   # 空だと静かに3次に落ちる
  • accelerations が空だとエラーにならず静かに3次に落ちる
  • 点が密なほど、次数が落ちたときの段差が頻繁に出る

入れる情報と補間次数の対応・比較アプリは「速度・加速度制御」の章

チェック③：時間パラメータ化はジャークを抑えているか

  • MoveIt 2 の既定 TOTG（Time-Optimal Trajectory Generation）は時間最適
  • 時間最適 ＝ 常にどこかの制約が飽和 ＝ 加速度は bang-bang
  • 5次で C² につないでも、入力の加速度が飽和値を行き来すれば急変する
  • ジャークを抑えたいなら Ruckig（MoveIt 2 の AddRuckigTrajectorySmoothing）

チェック④：密にしすぎても滑らかにはならない

  • 制御周期より短い区間は意味がない
    • UR：CB3 系 125 Hz（8 ms）、e-Series 500 Hz（2 ms）
  • 区間が極端に短いと5次多項式の係数が悪条件になり、わずかな不整合が高周波成分になる
  • 密にするほど、節点の不連続が高周波になるだけ
  • 滑らかさを決めるのは密度ではなく、節点での連続性の次数

※ 前章の「速度・加速度を 0」にする方法は、全点で止まる（全点が r = 0 の停止点）のと同じ。補間次数のアプリで確認できます

チェック⑤：角は密にしても消えない

  • 直交経路に鋭い角があると、密にサンプリングしても角は点と点の間に残る
  • 時間パラメータ化は加速度制約を守るので、角で自動的にほぼ停止まで減速
  • ＝ ブレンド半径を使わない代わりに、角で勝手に遅くなる
  • 速度を保ちたいなら、幾何の側で自前のブレンドやスプラインを入れる

「精度と速度の交換」はレイヤーを変えても消えない

おまけ：特異点

  • 直交空間で滑らか ≠ 関節空間で滑らか
  • 特異点の近くでは q′ = J⁻¹ v の関節速度が発散する
  • compute_cartesian_path に jump_threshold があるのはこのため
  • 密な IK サンプリング方式で一番危険なのはここ

特異姿勢の3種類は「step2:逆運動学」の章、ヤコビアンは「速度・加速度制御」の章のアプリで確認できます

実務上の判断

ジャークはまず問題にならない

  • 低速の動作
  • 軽いペイロード
  • 例：多くのラボオートメーション

ジャークが効いてくる

  • 高速の動作
  • 長い・柔らかいペイロード
  • 液体を持っている：液面のスロッシングが固有振動を持つ → こぼれ・液滴残り

  • C² には幾何と時間則の両方が滑らかである必要がある

  • コスト：障害物の距離を遠くなど
  • 最適化：確率的最適化
  • 軌道は最適化で決めるけど、最適化はサンプリングベースというハイブリッドっぽい
  • 滑らかさはCHOMPより劣るが解が収束しやすく実用上は使いやすい
